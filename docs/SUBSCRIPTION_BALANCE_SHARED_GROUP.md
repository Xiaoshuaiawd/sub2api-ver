# 同一分组支持订阅与余额的设计方案

日期：2026-10-09。目标仓库：`sub2api`。本文件记录混合计费实现方案和当前边界。

## 目标和默认行为

在现有分组计费类型 `standard`（余额）和 `subscription`（订阅配额）之外，新增第三种类型 `subscription_balance`。管理界面显示为**“配额优先（余额兜底）”**：同一个分组、同一把 API Key 先用该分组的有效订阅配额；没有可用订阅或订阅额度不足时，由用户余额支付整笔请求。**单笔请求只选一种资金来源，不拆分扣款。**

| 分组与状态 | 请求资金来源 |
| --- | --- |
| 标准分组 | 余额；沿用现有行为 |
| `subscription` 订阅分组 | 必须有有效订阅且未超限；沿用现有行为 |
| `subscription_balance` 混合分组，有可用订阅额度 | 订阅配额优先 |
| `subscription_balance` 混合分组，无订阅、已到期或额度不足 | 余额；先检查余额路径资格 |
| 两种来源均不可用 | 返回明确的额度不足错误，不调用上游 |
| 订阅服务/数据库不可用 | 返回服务错误；不要把服务故障误判成“订阅不足”并自动扣余额 |

“额度不足”包括日、周、月限额。现有订阅的其他状态错误，例如暂停与维护失败，按明确错误类型处理；只有业务上允许余额回退的状态才转到余额。现有 API Key 的独立额度和限速继续对两种来源生效。简易模式继续按现有规则跳过普通扣费。

余额兜底仅改变**资金来源**。第一版沿用同一分组现有模型价格、倍率和高峰倍率，避免同一请求因资金来源变化而出现未定义价格。若将来要求钱包价不同于订阅价，应像参考项目那样在选择来源时重新定价，并同时重算 Key 限额等派生金额；这应作为独立需求处理。

## 已确认的代码边界

当前 [分组类型](/Users/zhang/Downloads/桌面/副业类/sub2api/backend/internal/domain/constants.go:95) 将标准计费与订阅计费分开。主 [鉴权中间件](/Users/zhang/Downloads/桌面/副业类/sub2api/backend/internal/server/middleware/api_key_auth.go:193) 对订阅分组缺少订阅直接返回 403，Google 入口有相同独立判断。创建或绑定 API Key、获取可选分组时也以有效订阅作为订阅分组的必要条件。余额预留当前看到“订阅分组且订阅非空”就跳过。两条主要用量结算路径分别在 `gateway_usage_billing.go` 和 `openai_gateway_usage.go` 通过“分组类型 + 订阅指针”选择扣费类型。

当前 [结算命令](/Users/zhang/Downloads/桌面/副业类/sub2api/backend/internal/service/usage_billing.go:19) 已有 `SubscriptionCost`、`BalanceCost` 和请求幂等指纹，但构造时只填其中一种。现有 [数据库事务](/Users/zhang/Downloads/桌面/副业类/sub2api/backend/internal/repository/usage_billing_repo.go:175) 能更新两类账本，却不会检查“订阅本次金额是否仍在限额内并切换余额”。订阅 UPDATE 目前直接累加用量；请求入口的零增量限额检查不能防止并发完成时超限。

参考项目 `new-api-ver` 的 `BillingSession` 会按请求分组优先尝试订阅，订阅额度不足且允许溢出时改扣整笔钱包额度。它的 `available_groups` 属于订阅可用范围；本方案只复用扣费思路，不引入多分组订阅。参考项目还有一个需要避免的现状：当订阅覆盖分组时，`wallet_only` 设置仍会走订阅；本方案第一版不提供一个与实际行为不符的“钱包优先”选项。

## 数据与配置

`groups.subscription_type` 已是 `VARCHAR(20)`；`subscription_balance` 恰为 20 个字符，现有字段可容纳，不需为分组类型新增列。同步扩展领域常量、后端 `standard/subscription` 输入校验、API DTO、前端 `SubscriptionType` 联合类型和分组类型选择器。界面标签采用“配额优先（余额兜底）”，旁边说明“优先使用该分组的订阅配额；不可用或不足时由余额支付整笔请求”。旧分组仍是 `standard` 或 `subscription`，升级后行为不变。该名称描述的是**分组策略**；单次用量日志的 `billing_type` 仍只记录实际资金来源“余额”或“订阅”。

创建后也允许编辑分组平台和计费类型。后台 `UpdateGroup` 已能接收并保存这两个字段，平台变化还会失效渠道缓存；需要开放前端编辑选择器、显示即时生效的提示，并让订阅限额/高峰配置在纯订阅与混合类型中都可编辑。平台变更不自动删除旧账号绑定和价格配置；管理员保存后需要检查新平台可用账号、定价和映射。类型变更不删除既有订阅，但旧 API Key 下一次请求立即按新类型鉴权和计费。

不要仅把 `IsSubscriptionType()` 扩展为对两个类型都返回 true 后沿用全部调用点：订阅计划和高峰倍率需要识别两种支持订阅的分组，但 API Key 绑定、鉴权等“必须有订阅”的判断只适用于纯订阅类型。拆出语义明确的能力判断，例如 `UsesSubscriptionQuota()` 和 `RequiresSubscription()`，并逐处审查现有 `IsSubscriptionType()` 调用。若需要在去重记录和归档表中持久化本次实际资金来源，使用下一条迁移增加该字段；这与分组类型字段的存储无关。

## 请求与结算流程

1. **分组权限与绑定。** 有有效订阅的用户沿用现有绑定许可；该订阅也授权当前请求在配额耗尽时由余额兜底，即使专属分组没有单独的 `user_allowed_groups` 授权。对于 `subscription_balance` 分组中没有订阅的用户，只在其具备该分组的余额访问权限时允许绑定 API Key：公开分组遵循普通可绑定规则；专属分组须经过 `user_allowed_groups` 授权。已有 Key 在订阅过期后也要按同一规则重新检查权限。统一调整 API Key 创建、改绑、可选分组列表和请求期校验，避免只放开一个入口造成越权。
2. **选择本次资金来源。** 中间件查有效订阅及限额：混合类型且订阅可用时首选订阅；混合类型下无订阅或业务性超限时检查余额资格、用户×平台限额和 API Key 规则。选择余额后，给现有 `CheckBillingEligibility` / 在途余额预留传入余额模式，不因分组支持订阅而跳过预留。把“资金来源选择”做成请求级结果，供普通、OpenAI、Google 与 WebSocket 入口复用；不要在各 handler 中各写一份判断。
3. **在最终事务中处理竞争。** 上游完成后得到实际费用；在既有 request ID 幂等事务中，锁定有效订阅行并使用实际费用检查日、周、月窗口。订阅能承接则扣订阅；只有 `subscription_balance` 能在额度竞争失败且余额路径可用时改扣**整笔**余额。Key 与账号限额在同一事务按实际计费金额更新。订阅状态查询失败、数据库失败和实际限额不足必须有不同错误类型。数据库结算结果返回最终 `billing_type`、`subscription_id` 和余额状态。
4. **统一后续副作用。** 现有余额缓存失效、余额通知、用户×平台配额、订阅用量缓存、用量日志等都按**最终资金来源**执行。现在这些分支读取结算前的 `IsSubscriptionBill`；只改 SQL 会造成日志写“订阅”、实际扣“余额”。遇到结算失败时沿用错误记录及对账告警，不生成一条表示“已成功扣费”的日志。
5. **稳定幂等身份。** 现有指纹包括 `BillingType`、`SubscriptionID` 和两类扣费金额。混合模式的请求指纹应以稳定请求事实和候选金额构成，不把最终选中的资金来源当作输入；已存入去重表与归档表的旧版指纹必须保持兼容。将实际来源随结算去重记录持久化，重试同一 request ID 时返回原结果，避免限额变化后重新选择来源或把旧请求误报为冲突。

原余额路径在实际结算时可能出现余额透支，仓储会返回 `BalanceOverdrafted`。第一版应明确沿用此现有后扣规则，并针对混合模式的透支结果告警；若业务要求“绝不出现负余额”，需要增加请求前的强预授权/预留及实际费用差额处理，属于更大的计费改造，不能只靠入口余额检查承诺。

订阅准入后若并发结算抢先耗尽额度，最终事务会改扣余额并发出告警。由于该请求在准入时按订阅路径放行，余额及用户×平台配额的事前检查无法对这种竞态给出严格保证；和现有后扣余额路径一样，高并发在途请求可能透支或超过平台配额。需要硬上限时应单独实现按预估金额的原子余额预授权。

## 实施顺序与验证

建议按以下可独立核对的阶段实施，不一次性改写所有计费路径：

1. 第三种分组类型、后台 API 与权限规则；逐处拆分“支持订阅”和“必须订阅”的判断，回归旧分组行为。
2. 请求资金来源选择、主/Google 鉴权与余额预留；覆盖无订阅、订阅过期、限额耗尽、公开/专属分组权限。
3. 原子结算、幂等来源持久化、缓存与日志；覆盖并发超限、同 request ID 重试、余额透支和两种来源都不足。
4. 接通普通网关、OpenAI 网关和 WebSocket 的结算入口。异步批量图片仍使用独立的余额预扣和捕获流程；混合分组在任务提交前明确拒绝，待该流程支持订阅预留后再开放，避免实际扣费与分组策略不一致。
5. 在 `GroupsView.vue` 的类型选择中增加“配额优先（余额兜底）”及说明；编辑页开放平台和计费类型选择，并更新用户看到的分组可选性和消费记录展示。验证键盘操作、说明可读性、切换后的配置字段和状态回显。

验收条件：现有 `standard` 与 `subscription` 分组行为不变；选择 `subscription_balance` 后相同分组和 API Key 可先订阅配额、后余额；一次请求只扣一次、只记录一个正确的来源；并发触顶不超过订阅限额；重复请求和退款不会双扣；专属分组不会因为余额兜底而向未授权用户开放。完整回归还应包含简易模式、不同协议入口、失败流式请求及订阅维护窗口重置。
